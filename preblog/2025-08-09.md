# Comunicaciones cifradas con criptografia de curvas elipticas en Go: guia de implementacion practica

## Resumen

La criptografia de curvas elipticas (ECC, "Elliptic Curve Cryptography") ofrece niveles de seguridad equivalentes a RSA con claves significativamente mas cortas, lo que la hace especialmente adecuada para sistemas con restricciones de ancho de banda, latencia o recursos computacionales. Esta guia explica como implementar comunicaciones cifradas de extremo a extremo usando ECC en Go: generacion de pares de claves, acuerdo de clave compartida mediante ECDH, cifrado autenticado de mensajes con AES-GCM, y firma y verificacion con ECDSA. El modelo de comunicacion utilizado a lo largo de la guia es deliberadamente simple (dos partes, Alice y Bob, que intercambian mensajes cifrados) para que el foco este en los mecanismos criptograficos y no en la complejidad de la infraestructura.

---

## 1. Introduccion

Durante decadas, RSA fue el algoritmo de referencia para criptografia de clave publica. Su seguridad se basa en la dificultad de factorizar numeros enteros muy grandes, lo que exige claves de al menos 2048 bits para ser considerado seguro en la actualidad. La criptografia de curvas elipticas parte de un problema matematico diferente (el problema del logaritmo discreto sobre una curva eliptica) cuya dificultad computacional permite obtener el mismo nivel de seguridad con claves mucho mas cortas: una clave ECC de 256 bits es considerada equivalente en seguridad a una clave RSA de 3072 bits (NIST, 2020).

Esta diferencia tiene consecuencias practicas concretas. Las operaciones criptograficas son mas rapidas, los certificados y las firmas ocupan menos espacio, y la huella de memoria es menor, lo que hace a ECC la opcion preferida en protocolos modernos como TLS 1.3, SSH, Signal y las APIs de pago por contacto.

Go incorpora soporte nativo para ECC en su biblioteca estandar a traves del paquete `crypto/elliptic` y sus implementaciones especificas `crypto/ecdh` y `crypto/ecdsa`. Esto significa que no se necesitan dependencias externas para implementar un sistema de comunicacion cifrada completo y seguro: todo lo necesario esta disponible en la instalacion estandar del lenguaje.

Al final de esta guia se dispondrá de un sistema funcional donde Alice y Bob pueden intercambiar mensajes cifrados y firmados sin que un tercero que intercepte el trafico pueda leer el contenido ni suplantar a ninguna de las partes.

---

## 2. Fundamentos matematicos (lo necesario para implementar bien)

No es necesario dominar la teoria de grupos algebraicos para implementar ECC correctamente, pero entender tres conceptos evita errores de implementacion frecuentes.

Una curva eliptica sobre un campo finito es el conjunto de puntos (x, y) que satisfacen la ecuacion y^2 = x^3 + ax + b (mod p), donde p es un numero primo grande. Lo que hace util a esta estructura es que sobre ella se puede definir una operacion de "suma de puntos" que tiene propiedades algebraicas muy convenientes: es asociativa, conmutativa, y tiene un elemento neutro. A partir de esa suma se puede definir la "multiplicacion escalar": dado un punto G (llamado punto generador) y un entero k, el producto k*G significa sumar G consigo mismo k veces.

El problema del logaritmo discreto en curvas elipticas consiste en que, dados G y el punto Q = k*G, encontrar k es computacionalmente intratable para valores de k suficientemente grandes. Este es el fundamento de la seguridad de ECC: la clave privada es el escalar k, y la clave publica es el punto Q. Calcular Q a partir de k es rapido; calcular k a partir de Q es imposible en la practica.

Las curvas estandarizadas mas usadas son P-256 (tambien llamada secp256r1, recomendada por NIST para uso general), P-384 (mayor seguridad, usada en aplicaciones gubernamentales y financieras) y X25519 (disenada por Bernstein con propiedades de seguridad adicionales, preferida en protocolos modernos como TLS 1.3 y Signal). En esta guia se usara P-256 para ECDSA y X25519 para ECDH, que es la combinacion mas habitual en sistemas modernos.

## 3. Entorno de trabajo


Los paquetes que se importaran a lo largo de la guia son los siguientes:

```go
import (
    "crypto/ecdh"     // acuerdo de clave ECDH y gestion de claves de curvas
    "crypto/ecdsa"    // firma y verificacion ECDSA
    "crypto/elliptic" // definicion de curvas (P-256, P-384)
    "crypto/rand"     // fuente de aleatoriedad criptograficamente segura
    "crypto/sha256"   // hash para firmas
    "crypto/aes"      // cifrado simetrico AES
    "crypto/cipher"   // modo GCM para cifrado autenticado
    "encoding/pem"    // serializacion de claves en formato PEM
    "math/big"        // aritmetica de precision arbitraria para ECDSA
)
```

Una nota importante sobre la aleatoriedad: todas las operaciones criptograficas de esta guia usan `crypto/rand.Reader` como fuente de entropia, nunca `math/rand`. Esta distincion es critica: `math/rand` es un generador pseudo-aleatorio determinista pensado para simulaciones, completamente inadecuado para criptografia. Usar `math/rand` en lugar de `crypto/rand` para generar claves o vectores de inicializacion es uno de los errores de implementacion mas graves y frecuentes.

## 4. Generacion de pares de claves

El primer paso es que Alice y Bob generen cada uno su par de claves: una clave privada (que nunca se comparte) y una clave publica (que se puede distribuir libremente). En esta guia se generan dos pares: uno para ECDH (acuerdo de clave compartida, que se usara para derivar la clave de cifrado) y otro para ECDSA (firma digital, que se usara para autenticar los mensajes).

### 4.1 Claves para ECDH con X25519

```go
package main

import (
    "crypto/ecdh"
    "crypto/rand"
    "fmt"
)

func generarClavesECDH() (*ecdh.PrivateKey, *ecdh.PublicKey, error) {
    // X25519 es la curva recomendada para acuerdo de clave en sistemas modernos.
    // Fue disenada con propiedades que evitan clases enteras de ataques
    // presentes en las curvas NIST cuando se implementan descuidadamente.
    curva := ecdh.X25519()

    clavePrivada, err := curva.GenerateKey(rand.Reader)
    if err != nil {
        return nil, nil, fmt.Errorf("error generando clave ECDH: %w", err)
    }

    clavePublica := clavePrivada.PublicKey()
    return clavePrivada, clavePublica, nil
}

func main() {
    clavePrivAlice, clavePubAlice, _ := generarClavesECDH()
    clavePrivBob,   clavePubBob,   _ := generarClavesECDH()

    fmt.Printf("Clave publica Alice (hex): %x\n", clavePubAlice.Bytes())
    fmt.Printf("Clave publica Bob   (hex): %x\n", clavePubBob.Bytes())

    // Las claves privadas tienen 32 bytes; las publicas tambien en X25519.
    // En P-256 las claves publicas son puntos en formato comprimido (33 bytes)
    // o sin comprimir (65 bytes).
    _ = clavePrivAlice
    _ = clavePrivBob
}
```

### 4.2 Claves para ECDSA con P-256

```go
import (
    "crypto/ecdsa"
    "crypto/elliptic"
    "crypto/rand"
)

func generarClavesECDSA() (*ecdsa.PrivateKey, *ecdsa.PublicKey, error) {
    clavePrivada, err := ecdsa.GenerateKey(elliptic.P256(), rand.Reader)
    if err != nil {
        return nil, nil, fmt.Errorf("error generando clave ECDSA: %w", err)
    }
    return clavePrivada, &clavePrivada.PublicKey, nil
}
```

Es habitual tener estos dos pares separados porque sirven propositos distintos: las claves ECDH son efimeras en muchos protocolos (se regeneran por sesion para obtener "forward secrecy"), mientras que las claves ECDSA son de larga duracion y se asocian a la identidad de cada parte.

## 5. Acuerdo de clave compartida con ECDH

ECDH ("Elliptic Curve Diffie-Hellman") es el mecanismo que permite a Alice y Bob derivar un secreto compartido sin transmitirlo nunca por la red. La propiedad matematica que hace esto posible es que:

clavePrivAlice * clavePubBob = clavePrivBob * clavePubAlice = secreto compartido

Ambas partes realizan la misma operacion con su clave privada y la clave publica de la otra parte, y obtienen el mismo punto en la curva. Ese punto es el secreto compartido.

![Diagrama del acuerdo de clave ECDH entre Alice y Bob](/images/blog1b-ecdh.svg)

```go
import (
    "crypto/ecdh"
    "crypto/sha256"
    "fmt"
)

func derivarSecreto(clavePriv *ecdh.PrivateKey, clavePubRemota *ecdh.PublicKey) ([]byte, error) {
    // ECDH() devuelve el secreto compartido como bytes crudos.
    // Este valor NUNCA debe usarse directamente como clave de cifrado:
    // primero debe pasar por una funcion de derivacion de claves (KDF).
    secretoCrudo, err := clavePriv.ECDH(clavePubRemota)
    if err != nil {
        return nil, fmt.Errorf("error en ECDH: %w", err)
    }

    // SHA-256 como KDF minimalista. En produccion se prefiere HKDF (RFC 5869),
    // que permite incluir un "salt" y un contexto para derivar multiples claves
    // independientes del mismo secreto.
    hash := sha256.Sum256(secretoCrudo)
    return hash[:], nil // 32 bytes -> clave AES-256
}

func main() {
    clavePrivAlice, clavePubAlice, _ := generarClavesECDH()
    clavePrivBob,   clavePubBob,   _ := generarClavesECDH()

    // Alice calcula el secreto usando su clave privada y la publica de Bob
    secretoAlice, _ := derivarSecreto(clavePrivAlice, clavePubBob)

    // Bob calcula el secreto usando su clave privada y la publica de Alice
    secretoBob, _ := derivarSecreto(clavePrivBob, clavePubAlice)

    // Ambos secretos son identicos sin haberse transmitido nunca
    fmt.Printf("Secreto Alice: %x\n", secretoAlice)
    fmt.Printf("Secreto Bob:   %x\n", secretoBob)
    fmt.Printf("Identicos: %v\n", string(secretoAlice) == string(secretoBob))
}
```

El resultado de `derivarSecreto` es una clave de 32 bytes lista para usarse como clave AES-256. Es fundamental pasar el secreto crudo por una KDF antes de usarlo como clave: el secreto ECDH es un punto en la curva cuya distribucion no es uniforme, y usarlo directamente como clave simetrica debilita la seguridad del cifrado.

## 6. Cifrado autenticado con AES-GCM

Con la clave compartida derivada, Alice puede cifrar mensajes que solo Bob puede descifrar. El modo de operacion elegido es GCM ("Galois/Counter Mode"), que proporciona cifrado autenticado: ademas de confidencialidad, garantiza integridad y autenticidad del mensaje. Un mensaje modificado en transito producira un error de verificacion al descifrar, evitando ataques de manipulacion del ciphertext.

```go
import (
    "crypto/aes"
    "crypto/cipher"
    "crypto/rand"
    "fmt"
    "io"
)

func cifrar(clave []byte, mensaje []byte) ([]byte, error) {
    bloque, err := aes.NewCipher(clave)
    if err != nil {
        return nil, fmt.Errorf("error creando cifrador AES: %w", err)
    }

    gcm, err := cipher.NewGCM(bloque)
    if err != nil {
        return nil, fmt.Errorf("error creando GCM: %w", err)
    }

    // El nonce (numero usado una sola vez) debe ser unico para cada mensaje
    // cifrado con la misma clave. Reutilizar un nonce rompe la seguridad de GCM
    // de forma catastrofica: permite recuperar la clave de autenticacion.
    // Generarlo aleatoriamente con 12 bytes da una probabilidad de colision
    // negligible para volumenes de mensajes razonables.
    nonce := make([]byte, gcm.NonceSize()) // 12 bytes
    if _, err := io.ReadFull(rand.Reader, nonce); err != nil {
        return nil, fmt.Errorf("error generando nonce: %w", err)
    }

    // Seal cifra y autentica el mensaje. El nonce se antepone al ciphertext
    // para que el receptor pueda extraerlo al descifrar.
    // El cuarto argumento (nil aqui) son datos adicionales autenticados (AAD):
    // informacion que no se cifra pero si se autentica (por ejemplo, cabeceras).
    cifrado := gcm.Seal(nonce, nonce, mensaje, nil)
    return cifrado, nil
}

func descifrar(clave []byte, cifrado []byte) ([]byte, error) {
    bloque, err := aes.NewCipher(clave)
    if err != nil {
        return nil, fmt.Errorf("error creando cifrador AES: %w", err)
    }

    gcm, err := cipher.NewGCM(bloque)
    if err != nil {
        return nil, fmt.Errorf("error creando GCM: %w", err)
    }

    tamNonce := gcm.NonceSize()
    if len(cifrado) < tamNonce {
        return nil, fmt.Errorf("mensaje cifrado demasiado corto")
    }

    // Separar nonce y ciphertext
    nonce, ciphertext := cifrado[:tamNonce], cifrado[tamNonce:]

    // Open descifra y verifica la autenticidad. Si el mensaje fue modificado,
    // devuelve un error y no expone ningun byte del plaintext.
    mensaje, err := gcm.Open(nil, nonce, ciphertext, nil)
    if err != nil {
        return nil, fmt.Errorf("error de autenticacion: el mensaje fue alterado o la clave es incorrecta")
    }

    return mensaje, nil
}
```

La combinacion ECDH + AES-GCM implementa un esquema de cifrado hibrido: ECC resuelve el problema del intercambio de claves (que es el cuello de botella del cifrado simetrico puro), y AES-GCM resuelve el cifrado eficiente de datos de longitud arbitraria (que es el cuello de botella del cifrado asimetrico puro). Este patron es exactamente el que usa TLS internamente.

## 7. Firma y verificacion con ECDSA

El cifrado garantiza confidencialidad, pero no autenticidad: si Bob recibe un mensaje cifrado con la clave compartida, sabe que alguien con acceso a esa clave lo envio, pero no puede verificar que fue Alice y no un tercero que obtuvo la clave de alguna manera. ECDSA ("Elliptic Curve Digital Signature Algorithm") resuelve esto: Alice firma el mensaje con su clave privada de firma, y cualquiera que tenga su clave publica puede verificar que la firma es autentica y que el mensaje no fue modificado.

```go
import (
    "crypto/ecdsa"
    "crypto/rand"
    "crypto/sha256"
    "math/big"
)

func firmar(clavePriv *ecdsa.PrivateKey, mensaje []byte) ([]byte, []byte, error) {
    // ECDSA opera sobre el hash del mensaje, no sobre el mensaje directamente.
    // Esto permite firmar mensajes de longitud arbitraria con una operacion
    // de costo constante, y evita ataques que explotan la estructura del mensaje.
    hash := sha256.Sum256(mensaje)

    r, s, err := ecdsa.Sign(rand.Reader, clavePriv, hash[:])
    if err != nil {
        return nil, nil, fmt.Errorf("error firmando: %w", err)
    }

    // r y s son los dos componentes de la firma ECDSA.
    // En produccion se serializan juntos en formato DER (ASN.1) para
    // interoperabilidad con otros sistemas; aqui se devuelven separados
    // para claridad.
    return r.Bytes(), s.Bytes(), nil
}

func verificar(clavePub *ecdsa.PublicKey, mensaje []byte, rBytes []byte, sBytes []byte) bool {
    hash := sha256.Sum256(mensaje)

    r := new(big.Int).SetBytes(rBytes)
    s := new(big.Int).SetBytes(sBytes)

    // Verify devuelve true si y solo si la firma (r, s) es valida para
    // el hash del mensaje con la clave publica dada.
    return ecdsa.Verify(clavePub, hash[:], r, s)
}
```

Una advertencia importante sobre ECDSA: la firma requiere un numero aleatorio por operacion (el escalar k interno). Si ese numero se repite o es predecible, la clave privada puede recuperarse matematicamente a partir de dos firmas con el mismo k. Este ataque es real: fue el metodo usado para extraer la clave privada de las consolas PlayStation 3 en 2010. Go usa `crypto/rand.Reader` internamente en `ecdsa.Sign`, por lo que esta vulnerabilidad no aplica siempre que se use correctamente la biblioteca estandar.

## 8. Flujo completo de comunicacion

Con todos los componentes en su lugar, se puede construir el flujo completo de una comunicacion entre Alice y Bob: intercambio de claves publicas, derivacion del secreto compartido, cifrado y firma del mensaje por parte de Alice, y verificacion y descifrado por parte de Bob.

```go
package main

import (
    "crypto/ecdh"
    "crypto/ecdsa"
    "crypto/elliptic"
    "crypto/rand"
    "crypto/sha256"
    "crypto/aes"
    "crypto/cipher"
    "fmt"
    "io"
    "math/big"
)

func main() {
    // --- Fase 1: generacion de claves ---

    // Claves ECDH para acuerdo de secreto (X25519)
    clavePrivECDHAlice, clavePubECDHAlice, _ := generarClavesECDH()
    clavePrivECDHBob,   clavePubECDHBob,   _ := generarClavesECDH()

    // Claves ECDSA para firma (P-256)
    clavePrivECDSAAlice, clavePubECDSAAlice, _ := generarClavesECDSA()
    _, clavePubECDSABob,                     _ := generarClavesECDSA()

    // Bob no firma en este ejemplo, pero tendria su propio par de claves ECDSA
    _ = clavePubECDSABob

    // --- Fase 2: intercambio de claves publicas ---
    // En un sistema real esto ocurre a traves de un canal de distribucion
    // de claves (por ejemplo, certificados X.509 o un servidor de claves).
    // Aqui simplemente pasamos las variables en memoria.

    // Alice derativa el secreto con la clave publica de Bob
    secretoAlice, _ := derivarSecreto(clavePrivECDHAlice, clavePubECDHBob)

    // Bob deriva el mismo secreto con la clave publica de Alice
    secretoBob, _ := derivarSecreto(clavePrivECDHBob, clavePubECDHAlice)

    // Ambos tienen ahora la misma clave de cifrado sin haberla transmitido
    fmt.Printf("Secretos identicos: %v\n\n", string(secretoAlice) == string(secretoBob))

    // --- Fase 3: Alice cifra y firma un mensaje ---

    mensajeOriginal := []byte("Hola Bob. Este mensaje es confidencial y esta autenticado.")

    // Alice cifra el mensaje con la clave compartida
    mensajeCifrado, _ := cifrar(secretoAlice, mensajeOriginal)

    // Alice firma el mensaje en claro (no el cifrado) con su clave ECDSA privada.
    // Firmar el mensaje en claro permite a Bob verificar la autenticidad
    // antes o despues de descifrar, segun la politica del sistema.
    rFirma, sFirma, _ := firmar(clavePrivECDSAAlice, mensajeOriginal)

    fmt.Printf("Mensaje cifrado (%d bytes): %x...\n\n", len(mensajeCifrado), mensajeCifrado[:16])

    // --- Fase 4: Bob recibe, verifica y descifra ---

    // Bob descifra usando su copia del secreto compartido
    mensajeDescifrado, err := descifrar(secretoBob, mensajeCifrado)
    if err != nil {
        fmt.Println("Error al descifrar:", err)
        return
    }

    // Bob verifica la firma usando la clave publica ECDSA de Alice
    firmaValida := verificar(clavePubECDSAAlice, mensajeDescifrado, rFirma, sFirma)

    fmt.Printf("Mensaje descifrado: %s\n", mensajeDescifrado)
    fmt.Printf("Firma valida:       %v\n", firmaValida)
}
```

La salida esperada del programa es la siguiente:

```
Secretos identicos: true

Mensaje cifrado (73 bytes): a3f82c19d4b7e0f1...

Mensaje descifrado: Hola Bob. Este mensaje es confidencial y esta autenticado.
Firma valida:       true
```

## 9. Serializacion y persistencia de claves

En un sistema real las claves no viven solo en memoria: deben persistirse en disco, transmitirse en certificados o intercambiarse a traves de APIs. El formato estandar para esto es PEM ("Privacy Enhanced Mail"), que codifica los datos binarios en Base64 con cabeceras legibles.

```go
import (
    "crypto/ecdsa"
    "crypto/x509"
    "encoding/pem"
    "os"
)

func guardarClavePrivadaPEM(clave *ecdsa.PrivateKey, ruta string) error {
    // x509.MarshalECPrivateKey serializa la clave en formato SEC 1 / DER
    der, err := x509.MarshalECPrivateKey(clave)
    if err != nil {
        return fmt.Errorf("error serializando clave: %w", err)
    }

    f, err := os.OpenFile(ruta, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0600)
    if err != nil {
        return fmt.Errorf("error abriendo archivo: %w", err)
    }
    defer f.Close()

    // Permiso 0600: solo el propietario puede leer y escribir.
    // Guardar una clave privada con permisos mas permisivos es un error
    // de seguridad critico en sistemas multiusuario.
    return pem.Encode(f, &pem.Block{
        Type:  "EC PRIVATE KEY",
        Bytes: der,
    })
}

func cargarClavePrivadaPEM(ruta string) (*ecdsa.PrivateKey, error) {
    datos, err := os.ReadFile(ruta)
    if err != nil {
        return nil, fmt.Errorf("error leyendo archivo: %w", err)
    }

    bloque, _ := pem.Decode(datos)
    if bloque == nil || bloque.Type != "EC PRIVATE KEY" {
        return nil, fmt.Errorf("archivo PEM invalido o tipo incorrecto")
    }

    clave, err := x509.ParseECPrivateKey(bloque.Bytes)
    if err != nil {
        return nil, fmt.Errorf("error parseando clave: %w", err)
    }

    return clave, nil
}

func guardarClavePublicaPEM(clave *ecdsa.PublicKey, ruta string) error {
    der, err := x509.MarshalPKIXPublicKey(clave)
    if err != nil {
        return fmt.Errorf("error serializando clave publica: %w", err)
    }

    f, _ := os.OpenFile(ruta, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, 0644)
    defer f.Close()

    return pem.Encode(f, &pem.Block{
        Type:  "PUBLIC KEY",
        Bytes: der,
    })
}
```

Un archivo de clave privada generado por estas funciones tendría el siguiente aspecto:

```

-----END EC PRIVATE KEY-----
```

## 10. Modelo de amenazas y consideraciones de seguridad

La implementacion presentada en esta guia es correcta para los casos de uso descritos, pero es importante entender sus limites antes de usarla en un sistema de produccion.

El primer aspecto a considerar es la autenticacion de claves publicas. Esta guia asume que Alice y Bob obtienen las claves publicas del otro por un canal confiable. En la practica, un atacante activo puede interceptar ese intercambio y sustituir las claves publicas por las suyas propias (ataque "man in the middle"). Resolver esto requiere una infraestructura de confianza adicional: certificados firmados por una autoridad de certificacion (CA), un servidor de claves con registros de transparencia, o verificacion fuera de banda (como el mecanismo de "safety numbers" de Signal).

El segundo aspecto es el "forward secrecy". Si Alice y Bob reutilizan las mismas claves ECDH para multiples sesiones, un atacante que obtenga la clave privada de alguna de las partes en el futuro podra descifrar todas las comunicaciones pasadas que haya grabado. Para evitar esto, los protocolos modernos generan claves ECDH efimeras por sesion: las claves de larga duracion solo se usan para autenticar las efimeras, no para derivar directamente el secreto de sesion. Este es el patron que implementa el protocolo X3DH de Signal.

El tercer aspecto es la gestion del ciclo de vida de las claves privadas en memoria. Go tiene un recolector de basura que puede mover o copiar datos en memoria sin aviso. Para claves de alta sensibilidad, algunas implementaciones usan librerias que fijan los bytes de la clave en memoria y los sobreescriben con ceros antes de liberar. La biblioteca estandar de Go no proporciona esta funcionalidad de forma nativa; si es un requisito, existen paquetes como `golang.org/x/crypto/memguard` para cubrirlo.

## 11. Pruebas unitarias del sistema criptografico

Las implementaciones criptograficas son especialmente propensas a errores silenciosos: el codigo compila y ejecuta sin errores, pero la seguridad esta comprometida. Las pruebas unitarias son la primera linea de defensa.

```go
package main

import (
    "bytes"
    "testing"
)

func TestAcuerdoECDH(t *testing.T) {
    clavePrivA, clavePubA, err := generarClavesECDH()
    if err != nil {
        t.Fatalf("error generando claves A: %v", err)
    }
    clavePrivB, clavePubB, err := generarClavesECDH()
    if err != nil {
        t.Fatalf("error generando claves B: %v", err)
    }

    secretoA, _ := derivarSecreto(clavePrivA, clavePubB)
    secretoB, _ := derivarSecreto(clavePrivB, clavePubA)

    if !bytes.Equal(secretoA, secretoB) {
        t.Error("los secretos derivados no coinciden")
    }
}

func TestCifradoDescifrado(t *testing.T) {
    clave := make([]byte, 32)
    _, _ = rand.Read(clave)

    mensajeOriginal := []byte("mensaje de prueba con caracteres especiales: ñ, €, 中文")

    cifrado, err := cifrar(clave, mensajeOriginal)
    if err != nil {
        t.Fatalf("error cifrando: %v", err)
    }

    descifrado, err := descifrar(clave, cifrado)
    if err != nil {
        t.Fatalf("error descifrando: %v", err)
    }

    if !bytes.Equal(mensajeOriginal, descifrado) {
        t.Errorf("mensaje descifrado no coincide: got %q, want %q", descifrado, mensajeOriginal)
    }
}

func TestIntegridadGCM(t *testing.T) {
    clave := make([]byte, 32)
    _, _ = rand.Read(clave)

    cifrado, _ := cifrar(clave, []byte("mensaje de prueba"))

    // Modificar un byte del ciphertext debe causar fallo de autenticacion
    cifrado[len(cifrado)-1] ^= 0xFF

    _, err := descifrar(clave, cifrado)
    if err == nil {
        t.Error("se esperaba error de autenticacion al modificar el ciphertext, pero no se produjo")
    }
}

func TestFirmaVerificacion(t *testing.T) {
    clavePriv, clavePub, _ := generarClavesECDSA()
    mensaje := []byte("mensaje para firmar")

    r, s, err := firmar(clavePriv, mensaje)
    if err != nil {
        t.Fatalf("error firmando: %v", err)
    }

    if !verificar(clavePub, mensaje, r, s) {
        t.Error("la verificacion de la firma deberia ser valida")
    }

    // Una firma valida sobre un mensaje diferente no debe verificar
    if verificar(clavePub, []byte("mensaje diferente"), r, s) {
        t.Error("la firma no deberia verificar sobre un mensaje diferente")
    }
}
```

Ejecutar las pruebas:

```bash
go test ./... -v
```

La prueba `TestIntegridadGCM` es especialmente importante porque verifica que el modo GCM realmente rechaza ciphertexts modificados. Si este test pasa, se tiene evidencia de que el cifrado autenticado funciona correctamente y que un atacante que modifique el mensaje en transito no podra engañar al receptor.

## 12. Limitaciones y pasos siguientes

Esta implementacion es un punto de partida solido, pero tiene simplificaciones que conviene abordar antes de usarla en un sistema de produccion.

La primera es la KDF. Se uso SHA-256 directamente como funcion de derivacion de claves por simplicidad. En produccion se recomienda HKDF (RFC 5869), disponible en `golang.org/x/crypto/hkdf`, que permite incluir un contexto y un salt para derivar multiples claves independientes del mismo secreto compartido (por ejemplo, una clave de cifrado y una clave de autenticacion separadas).

La segunda es la serializacion de la firma. Los componentes r y s de la firma ECDSA se serializaron como bytes crudos por claridad. Para interoperabilidad con otros sistemas (certificados TLS, JWT, APIs de terceros) deben codificarse en formato DER usando `encoding/asn1`.

La tercera es la gestion de sesiones. Un sistema real necesita un protocolo de handshake que intercambie las claves publicas ECDH efimeras, autentique esas claves con las firmas ECDSA de larga duracion, derive las claves de sesion, y gestione la rotacion de claves. El protocolo Noise (usado por WireGuard y Signal) o TLS 1.3 son referencias excelentes para disenar este handshake.

Como siguiente paso natural, esta implementacion puede extenderse para construir un canal de comunicacion bidireccional completo sobre TCP o WebSockets, integrando las piezas de esta guia con el paquete `net` de Go y un protocolo de mensajes que incluya longitud, version y campos para las firmas y las claves efimeras.

## 13. Conclusion

Esta guia ha construido paso a paso un sistema funcional de comunicacion cifrada y autenticada usando exclusivamente la biblioteca estandar de Go. Los tres componentes centrales son ECDH con X25519 para el acuerdo de clave compartida, AES-GCM para el cifrado autenticado del contenido, y ECDSA con P-256 para la firma digital de los mensajes.

ECC en Go es accesible, eficiente y bien soportada por la biblioteca estandar: no se necesitan dependencias externas para implementar un sistema seguro. Los patrones descritos en esta guia (cifrado hibrido, forward secrecy con claves efimeras, autenticacion por firma digital) son los mismos que usan TLS 1.3, Signal y WireGuard, lo que significa que este codigo no es solo un ejercicio academico sino una base directamente aplicable a sistemas de produccion reales.
